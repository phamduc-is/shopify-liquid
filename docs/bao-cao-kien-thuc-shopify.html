Giá trị lớn nhất của Theme OS 2.0 không nằm ở cú pháp Liquid, mà nằm ở đường ranh giữa code và data: file .liquid định nghĩa luật (được phép có gì), file .json lưu thực thể (thực tế đang có gì). Nắm đúng ranh giới này thì merchant tự vận hành được store, dev chỉ can thiệp khi cần tính năng mới.

VD 1.1Nạp file CSS từ assets/ — vì sao không được viết thẳng đường dẫn

Bài toán Cần nạp theme.css đặt trong assets/. Không được hardcode URL vì Shopify đẩy asset lên CDN và gắn version để cache-busting.

Code Liquid — layout/theme.liquid

{{ 'theme.css' | asset_url | stylesheet_tag }}
{{ 'icon-cart.svg' | asset_url }}

Output HTML thật

<link href="//store.myshopify.com/cdn/shop/t/2/assets/theme.css?v=41827…"
      rel="stylesheet" type="text/css" media="all">
//store.myshopify.com/cdn/shop/t/2/assets/icon-cart.svg?v=93110…

Chuỗi ?v=… do Shopify tự sinh theo nội dung file: sửa CSS thì version đổi, trình duyệt tải bản mới. Hardcode /assets/theme.css thì mất hoàn toàn cơ chế này.

VD 1.2Đặt file sai thư mục — Shopify báo lỗi như thế nào

Bài toán Viết component product-price.liquid nhưng để lẫn vào sections/ thay vì snippets/, rồi gọi bằng {% render %}.

Code Liquid

{% render 'product-price', product: product %}
{% comment %} file thật đang nằm ở sections/product-price.liquid {% endcomment %}

Output — lỗi in thẳng ra trang

Liquid error (line 12): Could not find asset snippets/product-price.liquid

Đây là một trong ít trường hợp Shopify báo lỗi rõ ràng: {% render %} luôn tìm trong snippets/, {% section %} luôn tìm trong sections/. Sai thư mục là hỏng ngay, không im lặng như phần lớn lỗi khác trong Phụ lục A.

VD 2.1Trang chủ ghép từ những file nào — và Shopify tự bọc thêm thẻ gì

Bài toán Trang chủ cần hero slideshow rồi tới featured collection. Cần biết chính xác HTML cuối cùng gửi về browser trông ra sao.

Code — templates/index.json

{
  "sections": {
    "hero":     { "type": "slideshow",          "settings": {} },
    "featured": { "type": "featured-collection", "settings": {} }
  },
  "order": ["hero", "featured"]
}

Code — layout/theme.liquid

<body>
  {% sections 'header-group' %}
  <main>{{ content_for_layout }}</main>
  {% sections 'footer-group' %}
</body>

Output HTML

<body>
  <div id="shopify-section-sections--…__header" class="shopify-section">…</div>
  <main>
    <div id="shopify-section-template--…__hero" class="shopify-section">…slideshow…</div>
    <div id="shopify-section-template--…__featured" class="shopify-section">…</div>
  </main>
  <div id="shopify-section-sections--…__footer" class="shopify-section">…</div>
</body>

Hai điều rút ra: thứ tự trong order[] quyết định thứ tự DOM, và Shopify tự bọc mỗi section trong một thẻ có id="shopify-section-…" + class shopify-section. Thẻ bọc mặc định là div, đổi được bằng field "tag" trong {% schema %}.

VD 2.3Merchant tự chèn announcement bar phía trên header — dev không sửa code

Bài toán Sếp yêu cầu thêm thanh thông báo "Freeship đơn trên 500k" phía trên header. Nếu header viết bằng {% section 'header' %} thì phải sửa layout; dùng Section Group thì merchant tự làm.

Code — sections/header-group.json (trước)

{
  "type": "header",
  "sections": { "header": { "type": "header", "settings": {} } },
  "order": ["header"]
}

Code — sau khi merchant kéo-thả trong Theme Editor

{
  "type": "header",
  "sections": {
    "announcement": { "type": "announcement-bar",
                      "settings": { "text": "Freeship đơn trên 500k" } },
    "header":       { "type": "header", "settings": {} }
  },
  "order": ["announcement", "header"]
}

Output HTML — thứ tự đổi theo

<div class="shopify-section announcement-bar">Freeship đơn trên 500k</div>
<div class="shopify-section site-header">…</div>

File layout/theme.liquid vẫn chỉ có đúng một dòng {% sections 'header-group' %} — không đổi một ký tự. Thay đổi nằm hết trong file JSON do Theme Editor tự ghi.

{% for product in collection.products %}
  <li>{{ product.title }}</li>
{% endfor %}
<p>Tổng: {{ collection.products_count }} sản phẩm</p>

VD 3.1Badge trạng thái sản phẩm — 3 nhánh loại trừ nhau

Bài toán Thẻ sản phẩm hiển thị đúng một badge: hết hàng, đang giảm giá, hoặc đang bán bình thường. Ba trạng thái loại trừ nhau nên phải dùng elsif, không phải ba khối if rời.

Code Liquid

{% assign product_price = 40000 %}
{% assign compare_price = 50000 %}
{% assign available = true %}

{% if available == false %}
  <span class="badge badge--sold-out">Hết hàng</span>
{% elsif compare_price > product_price %}
  <span class="badge badge--sale">Đang giảm giá</span>
{% else %}
  <span class="badge badge--normal">Đang bán</span>
{% endif %}

Output HTML

<span class="badge badge--sale">Đang giảm giá</span>
VD 3.2unless — chỉ chạy khi điều kiện là false

Bài toán Hiện cảnh báo hết hàng. Viết {% if available == false %} cũng được, nhưng unless đọc gọn hơn khi chỉ có đúng một nhánh phủ định.

Code Liquid

{% assign available = false %}

{% unless available %}
  <p class="text-error">Sản phẩm này tạm thời hết hàng</p>
{% endunless %}

Output HTML

<p class="text-error">Sản phẩm này tạm thời hết hàng</p>

unless không có elsif. Cần nhiều nhánh thì phải quay về if / elsif.

VD 3.3case / when — so khớp một biến với nhiều giá trị

    <p>Danh mục: Áo sơ mi</p>
  {% when 'Pants' %}

VD 3.11Filter chaining làm sạch meta description cho SEO

Bài toán Mô tả sản phẩm merchant nhập là HTML có thẻ và dài hàng nghìn ký tự. Thẻ <meta name="description"> cần text thuần, tối đa ~160 ký tự, và an toàn khi nhúng vào attribute.

Code Liquid — snippets/meta-tags.liquid

<meta name="description" content="
  {{- product.description | strip_html | truncate: 160 | escape -}}
">

Thứ tự filter có ý nghĩa: strip_html phải chạy trước truncate, nếu không 160 ký tự đầu có thể bị thẻ HTML chiếm hết. escape chạy cuối để đổi & thành &amp;, tránh làm hỏng attribute.

NHÓM 05 Ngày 6

Component hoá: snippet & {% render %}

Coi snippet như một hàm: có input khai báo rõ, không đọc biến ngoài phạm vi. Đây là nhóm kiến thức tạo ra khác biệt lớn nhất về khả năng bảo trì.

render vs include

render — chuẩn OS 2.0

Chạy trong isolated scope: không kế thừa biến local của file cha (trừ object toàn cục).

Tránh đụng độ tên biến, và được Shopify cache → nhanh hơn nhiều lần.

include — deprecated

Kế thừa toàn bộ biến từ file cha.

Dễ xung đột tên biến, không cache được, giảm hiệu năng. Không dùng cho code mới.

Năm dạng cú pháp {% render %}

DạngCú phápDùng khi
1 · Cơ bản{% render 'header-icon' %}Snippet chỉ đọc HTML tĩnh hoặc object toàn cục (icon SVG, thông tin shop)
2 · Truyền tham số{% render 'product-price', product: item, price_color: 'red' %}Truyền nhiều biến cùng lúc — dạng nên dùng làm mặc định

VD 9.1Ô search hoạt động thật — và điều gì xảy ra khi đặt sai name

Bài toán Ô tìm kiếm trong header phải submit được, URL kết quả phải share/bookmark được, và khi vào trang kết quả thì từ khoá vừa gõ vẫn còn trong input.

Code — sections/header.liquid

<form action="{{ routes.search_url }}" method="get" role="search">
  <input type="search" name="q" value="{{ search.terms | escape }}"
         placeholder="{{ 'general.search.placeholder' | t }}">
  <button type="submit">{% render 'icon-search' %}</button>
</form>

Output HTML — ở trang chủ

<form action="/search" method="get" role="search">
  <input type="search" name="q" value="" placeholder="Tìm sản phẩm...">
  <button type="submit"><svg>…</svg></button>
</form>

Hành vi — gõ "áo thun" rồi Enter

Browser tự ghép query string từ thuộc tính name:
  → /search?q=áo+thun

Output HTML ở trang kết quả (search.terms giờ đã có data):
  <input type="search" name="q" value="áo thun" …>   ← từ khoá được điền lại

Nếu đặt name="search" thay vì name="q"

  → /search?search=áo+thun

Trang /search VẪN load bình thường, không lỗi gì,
nhưng luôn ra "0 kết quả" — vì backend Shopify chỉ đọc key "q".

Cả form không cần một dòng JS: method="get" khiến browser tự làm việc ghép query string, lấy name làm key.

VD 9.2Setting link_list — merchant đổi menu, HTML đổi, code không đổi

Bài toán Header và footer đều render menu, nhưng dùng 2 menu khác nhau trong Admin. Không được hardcode linklists['main-menu'] vì mỗi store đặt tên menu khác nhau.

Code — {% schema %}, cho merchant tự chọn menu

"settings": [
  { "type": "link_list", "id": "menu",
    "label": "Menu điều hướng", "default": "main-menu" }
]

Code Liquid — dùng chung cho mọi menu

{%- for link in section.settings.menu.links -%}
  <a href="{{ link.url }}">{{ link.title }}</a>
{%- endfor -%}

Output — section header, merchant chọn "Main menu"

<a href="/">Trang chủ</a>
<a href="/collections/all">Cửa hàng</a>
<a href="/pages/lien-he">Liên hệ</a>

Output — cùng đoạn code đó ở footer, merchant chọn "Footer menu"

<a href="/pages/chinh-sach-doi-tra">Chính sách đổi trả</a>
<a href="/pages/bao-mat">Bảo mật</a>

Merchant sau đó đổi "Cửa hàng" trỏ từ /collections/all sang collection "Hàng mới về" — link.url tự resolve thành /collections/hang-moi-ve, dev không biết và cũng không cần biết.

VD 9.3Ba bước từ HTML tĩnh sang động — cùng một icon cart

Bài toán Vừa clone xong header từ Figma, markup đang là HTML tĩnh với số "3" gõ cứng. Đi đúng thứ tự 3 bước để không phải sửa lại layout khi bind data.

Bước 1 — HTML tĩnh, data giả (chốt layout & CSS trước)

<a href="/cart" class="header__cart">
  <img src="icon-cart.svg" alt="">
  <span class="header__cart-badge">3</span>
</a>

Bước 2 — bind object có sẵn (chưa cần schema)

<a href="{{ routes.cart_url }}" class="header__cart">
  {% render 'icon-cart' %}
  {%- if cart.item_count > 0 -%}
    <span class="header__cart-badge">{{ cart.item_count }}</span>
  {%- endif -%}
</a>

Output sau bước 2 — đã sống thật

<a href="/cart" class="header__cart">
  <svg class="icon icon-cart">…</svg>
</a>
<!-- badge tự biến mất vì giỏ đang rỗng, không cần merchant cấu hình gì -->

Bước 3 — thêm schema cho phần cần merchant nhập

{% comment %} Code Liquid viết trước, tạm rỗng vì chưa có schema {% endcomment %}
{%- if section.settings.show_cart_label -%}
  <span class="header__cart-text">{{ 'general.cart' | t }}</span>
{%- endif -%}

{% schema %}
{
  "settings": [
    { "type": "checkbox", "id": "show_cart_label",
      "label": "Hiện chữ cạnh icon giỏ hàng", "default": false }
  ]
}
{% endschema %}

Vì sao đúng thứ tự này quan trọng: bước 2 cho kết quả nhìn thấy ngay mà không phụ thuộc gì; nếu làm ngược (viết schema trước) thì suốt quá trình dựng layout mọi thứ đều rỗng, không biết CSS đã đúng chưa.
